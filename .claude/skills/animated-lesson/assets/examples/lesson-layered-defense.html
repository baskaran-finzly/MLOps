Six questions

One question per concept

If you remember only one thing from this lesson, remember the question each concept answers. The kitchen is the same trainee chef from Lesson 1.

ToolsWhat can it do at all?The equipment in the kitchen. No deep fryer means no frying, whatever anyone wants.
EnvironmentWhere does it run, and what is within reach there?A training kitchen with practice ingredients, or the real restaurant on a Saturday night.
PermissionsWhich actions may it take without asking?May use the stove. Must ask before the fryer. May never enter the cold room.
ConstraintsHow far, how much, how long?Your station only. Twenty minutes per dish. At most two pinches of saffron.
PoliciesWho sets the rules, and do they apply to everyone?Head office rules for every branch. A branch manager can't change them.
GuardrailsWhat catches a bad action the moment it happens?The gas valve that cuts off when the flame goes out. The allergen check at the pass.
Defense in depth

Every layer has holes. Together they don't.

Engineers call this the Swiss cheese model. Each layer stops some bad actions and misses others. Stack them, and almost nothing gets through all of them. Watch nine actions an agent might try, and where each one stops.

    Notice the first stop: a tool that doesn't exist is the strongest restriction of all. You don't need a rule against sending emails if the agent has no way to send one.

    The six concepts

    One at a time

    Don't mix these up

    Permission vs guardrailA permission matches the action's name or pattern: Bash(git push *). A guardrail looks at what is actually being done: the file path, the diff, the content.
    Permission vs constraintA permission says yes or no. A constraint sets a limit on something that is allowed: how long, how many turns, how much money, which folders.
    Policy vs permissionA policy is the decision ("no agent touches production"). Permissions, sandboxes and environments are how that decision is carried out.
    Permissions in Claude Code

    Six permission modes

    A permission mode sets the baseline for what runs without asking. Your allow, ask and deny rules sit on top. Pick a mode and watch five typical actions change.

    Two lines from the docs to remember. "Deny rules block in every mode, including bypassPermissions." And about auto mode: it "reduces permission prompts but does not guarantee safety." Cycle modes with Shift+Tab, or start with claude --permission-mode plan.

    Why both?

    When an allowed command does more than its name says

    Your rules allow ./mvnw test. But a test, or a compromised dependency, can run any code it likes. Permission rules are checked before a command starts. The sandbox is enforced by the operating system while the command runs.

    The permission rule says yes to ./mvnw test. It can't see what the tests will do once they start.

    The docs put it plainly: the sandbox boundary "holds regardless of what the model chose to run and even if an allowed command does more than its name suggests." It covers shell commands only. Claude's own file tools, MCP servers and hooks run outside it, so they still need permission rules. Each layer covers the other's gap.

    Apply it

    Upgrade your payment service

    Your sample-payment-service has permissions and one guardrail already. Here are the other layers, ready to try. As in Lesson 4, they're left for you to add.

    Permissions · add an "ask" rule

    Limits live in application.yml. Changing one changes how money moves, so make the agent stop and ask. An ask rule wins over any allow rule.

    "ask": [
  "Edit(./src/main/resources/application.yml)"
]
    Guardrail · no card numbers in code

    A PreToolUse hook that inspects what is about to be written, not just where:

    #!/usr/bin/env bash
c=$(jq -r '.tool_input.content
  // .tool_input.new_string // empty')
if grep -Eq '\b([0-9]{4}[ -]?){3}[0-9]{4}\b' \
    <<< "$c"; then
  echo "Blocked: looks like a card number." >&2
  exit 2
fi

    It will also flag some harmless 16-digit IDs. Measuring false alarms like that is Lesson 6.

    Environment · turn on the sandbox

    Shell commands may write only inside the project, and may reach only Maven Central. Watch the trap: if you block reading your home folder, Maven can't read its cache in ~/.m2 and every build fails. A harness that breaks the build is a harness people switch off.

    "sandbox": {
  "enabled": true,
  "filesystem": { "denyRead": ["~/"], "allowRead": [".", "~/.m2"] },
  "network":    { "allowedDomains": ["repo.maven.apache.org"] }
}

    Built from the documented keys. The sandbox runs on macOS (Seatbelt), Linux and WSL2 (bubblewrap); on native Windows commands run unsandboxed. It doesn't restrict the Read tool, so keep your Read(./.env) deny rule too. Rerun scripts/test-harness.sh after turning it on.

    Policy · organization-wide

    Deployed by IT as managed settings. Nothing in user or project settings overrides it, and its deny rules add to everyone's.

    {
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Read(**/application-prod.yml)",
      "Bash(kubectl *)"
    ]
  }
}
    Constraints · an unattended CI run

    When nobody is watching, cap turns and spend, and deny anything not pre-approved:

    claude -p "Fix the failing PaymentFlowTest" \
  --permission-mode dontAsk \
  --allowedTools "Read" "Edit" \
                 "Bash(./mvnw -q test *)" \
  --max-turns 30 \
  --max-budget-usd 2
    In one sentence

    Tools decide what is possible, the environment decides what is within reach, permissions decide what needs asking, constraints set the limits, policies make the rules the same for everyone, and guardrails catch what slips through at the moment it happens.
